# Резервное копирование и восстановление

Ежедневная копия хранится в `/opt/paperclip/backups`, семь дней, права root-only.
Она содержит PostgreSQL, конфигурацию и секреты Paperclip, профили OAuth,
checkout и Git-объекты, состояние исполнителей, регистрацию ролей, runtime и
systemd/AppArmor definitions. Каталоги зависимостей, загрузки и диагностические
логи не включаются; pinned toolchains восстанавливаются установочными скриптами.
Копия на этом VPS не защищает от полной потери сервера.

`swarm/scripts/backup.sh` берёт общий heavy-stage lock. При занятом исполнителе
копирование ждёт освобождения до восьми часов; превышение даёт exit75. Возраст lock не является основанием его
удалить. Сначала останавливается служба исполнителей и снимается её файловый архив при
работающем интерфейсе Paperclip. Затем Paperclip кратко останавливается для dump
и снимка конфигурации. Сжатие архивов происходит после возврата обеих служб. PostgreSQL
остаётся доступным только внутри Compose. Trap возвращает ранее активные службы.
Незавершённые `.partial-*` копии не выдаются за готовые.

Порядок проверки на сервере:

```sh
/opt/paperclip/scripts/backup.sh
/opt/paperclip/scripts/verify-backup.sh /opt/paperclip/backups/TIMESTAMP
```

Проверка создаёт отдельную временную БД, восстанавливает dump с exit-on-error и
сравнивает fingerprint содержимого всех таблиц с моментом снимка. Сравнивать с
уже перезапущенной live-БД неправильно: её audit/heartbeat записи изменяются.
Архив исполнителей распаковывается в приватный временный каталог; проверяются
регистрации, профили и права auth.json. Затем удаляются только созданные этой
проверкой временная база и временный каталог.

25.09.2026 проверен снимок `20260925T002721Z`: SHA256 трёх архивов и fingerprint,
210 таблиц, точное совпадение строк с исходным снимком, конфигурации приложения,
профилей и регистрации исполнителей. После рестарта повторно прошли sandbox
probes; Paperclip `/api/health` вернул `ok`. Первую копию `20260925T002430Z`
сохраняем: её restore прошёл, но старое сравнение с live-БД закономерно не совпало.

Для аварийного восстановления сначала остановить запись и сохранить текущие
данные отдельным снимком. Развернуть копию в новом каталоге/новых volumes,
восстановить БД и файлы с исходными UID/правами, установить pinned runtime,
загрузить AppArmor и systemd, проверить health и изоляцию, затем переключить
рабочую конфигурацию. Не распаковывать архив поверх работающей production-системы.
Не использовать `down -v`. После миграций БД откат одного образа не считается
безопасным: восстанавливать согласованный снимок приложения и БД.

Чистая полная реконструкция VPS и восстановление source-built образа форка ещё
не проверены; текущий PASS относится к отдельной БД и извлечённым файлам.

## Личный GitHub OAuth публикатора

С 25.09.2026 worker archive включает `/var/lib/loginom-swarm-publisher`.
Это секретный профиль отдельного системного пользователя; архив остаётся root-only.
После переноса на новый VPS выполнить `install-publisher.sh`, восстановить профиль,
исправить владельца на созданный loginom-publisher и проверить 0700/0600.
`verify-backup.sh` сравнивает восстановленный credential с текущим без вывода
содержимого. `verify-publisher.py` отдельно проверяет актуальность OAuth и права.
Если GitHub отозвал токен, требуется новый device-вход; восстановление файла
само по себе не восстанавливает отозванные права. Подробности в GITHUB-PUBLICATION.md.
