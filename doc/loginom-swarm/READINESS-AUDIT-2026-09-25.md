## Оставшиеся работы в порядке зависимостей

### 1. Рабочий исполнитель и координатор — критический блок

Сейчас `swarm/runtime/worker.py` отклоняет все POST, кроме `/v1/probe`.
`worker_client.py` также разрешает только health/probe. `evidence.py` содержит
проверки полей, но не вызывает роли и не сохраняет ход кампании. Подключения
Swarm runtime к серверному коду Paperclip в проверенных путях не найдено.

Нужно реализовать ограниченный протокол запуска/статуса/отмены этапа, связать его
со штатными задачами/cases, leases и expectedVersion. Использовать авторитетное
состояние Paperclip, не создавать параллельную базу очереди. На каждый шаг нужны
устойчивый идентификатор операции, восстановление после сбоя и дедупликация.

Обязательны реальные ограничения двух исправлений, 8 часов активной обработки,
30 минут приёмки, одного тяжёлого этапа; общая блокировка Loginom agent. Сейчас
есть heavy lock для инфраструктурных проверок, а полный жизненный цикл этих
ограничений отсутствует. Неизвестная мутация/cleanup переводит в blocked;
осиротевший lock требует reconciliation, не удаления по возрасту.

Готово, когда диагностическая кампания на уже поддерживаемом узле проходит весь
путь через штатный UI/API и безопасно продолжает работу после остановки службы.
Sampling до передачи пользователю не запускать.

### 2. Настоящая интеграция OpenViking — критический блок

Есть только `swarm/memory/gateway_policy.py` и отрицательные тесты.
Профильная systemd-служба памяти на VPS не найдена; README прямо отмечает отсутствие
подключённого gateway. Policy сама по себе не доказывает регистрацию настоящего thread.

Нужно: отдельная служба со своим UID и мастер-ключом вне моделей; ограничение точным
каноническим Peer; доверенная регистрация серверных checkout; immutable Linux hooks;
реальные Codex thread ID; доказательство SessionStart и завершённого подготовительного
хода; отдельные capture cursors разработчика и ревьювера; capture/extraction через
штатные API; продолжение сессии и обратное чтение результата из основной задачи Mac.
Проверить отказ чужому Peer/сессии/приёмщику и невозможность прямых записей в peers.
Локальная генерация 20260924.1 остаётся прежней.

### 3. Конфигурация процесса Paperclip и ручной старт — критический блок

API показал case sampling-pilot в `setup`, manualStart=false, activeWork=null,
liveness=no_action_path. Все четыре роли paused. Reviewer, acceptance и publisher
исполняют `/usr/bin/false`; developer всё ещё использует прежний pilot-codex.
В pipeline 13 этапов, **transitions=[]**, **documentKeys=[]**.

Нужно задать разрешённый граф переходов, документы результатов и связи задач,
назначить рабочие адаптеры, подключить запуск/продолжение собственных сессий и
правильного независимого ревьювера. При enforceTransitions=true отсутствие ребра
отклоняет штатный transition (см. server/src/services/pipelines.ts), даже если
UI выдаёт все этапы в allowedNextStages. Не обходить это постоянным force.

В текущем upstream `autonomy=auto` явно отклоняется с autonomy_not_enabled.
Нельзя рассчитывать, что переключатель auto запустит Swarm. Сначала проверить
служебную координацию через доступный transition API с leases/version и выбранной
идентичностью агента. Если штатных контрактов недостаточно, минимальную правку
upstream обосновать и внести в реестр. Не ослаблять конечное человеческое решение.

Ручной старт должен фиксировать инициатора kartamyshev, точный базовый commit,
один узел и единственный campaign/run. Отдельно подготовить действия остановки,
разбора blocked и безопасного продолжения; никаких расписаний и следующего узла.

### 4. Loginom, сборка кандидата и независимая приёмка — критический блок

`build_probe.py` жёстко использует исходный f81ebded и infrastructure workspace.
`build-cli-candidate.sh` ожидает уже зафиксированный исходный commit и не обновляет
имеющийся source checkout на следующий исправленный кандидат.
`sandbox.py` монтирует приёмщику только `0.1.16-prod`.
Профиль `/opt/loginom-worker/profiles/sampling/loginom-development` отсутствует.

Нужно связать reviewed commit → чистая полная CLI-сборка → manifest/hashes →
установка именно этого кандидата в изолированное окружение приёмки. Переключение
на новый candidate после исправлений должно быть явным, а не наложением исходников
на старый bundle. Приёмщик не получает .git разработки, историю исправлений,
память разработчика и ожидаемые результаты.

Подготовить отдельный Loginom доступ разработчика, затем проверить штатным CLI
на уже поддерживаемом узле: бизнес-ТЗ и данные → пакет → выполнение → сохранение →
независимое повторное открытие → проверка результатов служебным кодом → cleanup.
Семантика Sampling, входные данные и независимый эталон должны быть подготовлены
в согласованной фазе перед разработкой; инфраструктурная проверка не заменяет это.

### 5. Автоматическая публикация от kartamyshev-dev

Личный доступ и реальный тестовый push/PR уже готовы; OAuth заново не требуется.
Но `verify-publisher.py` только читает API, а служебного publish-протокола ещё нет.

Нужно подключить отдельный UID publisher к координатору: принимать только
зафиксированный кандидат с проверенной цепочкой review/build/acceptance;
проверять инициатора и GitHub identity; push новой ветки и один PR в loginom;
сохранять branch/commit/PR в case; после неопределённого ответа сначала искать
существующий результат. Не исполнять код, hooks или Git config кандидата рядом
с личным токеном. Без force push, автоматического merge или релиза.

### 6. Сквозные проверки перед открытием запуска

После сборки компонентов проверить целый цикл на поддерживаемом узле, включая:

- точные модели под каждым итоговым профилем и отсутствие молчаливой подмены;
- перезапуск и продолжение thread/checkouts/memory cursors;
- повтор события без второго run/PR, конкурентный старт и общую блокировку;
- отмену активного процесса и подтверждённый cleanup;
- потерю памяти/OAuth/Loginom, провал ревью или приёмки без ложного PASS;
- два исправления, временные ограничения, неизвестный исход мутации;
- очистку реальных логов до записи, отсутствие reasoning и секретов в артефактах;
- пиковые RAM/disk/OOM и стабильность Paperclip именно при полной приёмке.

Чистые функции evidence сейчас доверяют переданным status/hash полям. Координатор
должен сам получать и проверять соответствующие артефакты и их происхождение;
нельзя принять JSON от модели как достаточное доказательство PASS.

### 7. CI, обновление upstream и развёртывание форка

PR #1 остаётся draft; default branch swarm есть, но bootstrap ещё не принят туда.
На 01:22 UTC run 36081258897: contracts PASS, application/image выполняются.
Старый run 36078532502 ещё выполняет test:run. Не объявлять CI зелёным и не
перезапускать его без причины: частые push уже отменяли предыдущие проверки.

Нужно получить полный результат CI, разобрать реальные падения/зависания,
закончить review/приёмку bootstrap. Ручные update/release workflows пока
подготовлены, но не испытаны в GitHub. Локальные временные Git-тесты merge/conflict
не заменяют запуск workflow, проверку прав создания PR и публикации образа.

Затем собрать и опубликовать финальный образ из точного commit форка, закрепить
digest; проверить запуск и миграции на восстановленной копии БД; сделать backup;
отдельно установить образ и согласованную версию host runtime. Сейчас installer
host-worker рассчитан на bootstrap и отказывает при существующей службе — нужен
документированный механизм обновления/отката связанной пары runtime + container.
Проверить совместимость протокола, реальную UID/socket доступность и сохранение данных.

Откат образа не заменяет восстановление БД после несовместимых миграций. Старый
SSH-пилот архивировать только после проверки полного нового пути.

### 8. Восстановление и передача

После добавления памяти/координатора расширить backup на их регистрации, cursors,
состояние и артефакты. Проверить восстановление всей связанной системы, а не только
БД/профилей по отдельности. Toolchain/CLI должны воспроизводимо устанавливаться с
исходными manifest modes; учесть восстановление UID и необходимость повторного OAuth.

Подготовить короткие инструкции пользователя: старт одного Sampling, где читать
прогресс и результаты, остановка, blocked/reconciliation, продолжение, ссылка на PR.
Только после всех проверок перевести case в готовность к ручному старту.

## Что требуется от пользователя

Новых продуктовых решений сейчас не требуется. Доступ GitHub к чужому репозиторию
решён личным OAuth; установка App владельцем больше не блокирует работу. Память,
Loginom и модели интегрируются в рамках уже согласованного решения. Новый OAuth
понадобится только при истечении/отзыве авторизации. Увеличение VPS — только если
измерение полной приёмки нарушит порог 512 MiB / 20 GiB или выявит OOM.

Внешние backup-копии полезны, но не являются незавершённым требованием первой
установки: пользователь согласовал семь дней на том же VPS.
