# Обновление Paperclip и отдельное развёртывание

Основная ветка форка — `swarm`; `master` не содержит наших доработок.
Начальная база: `v2026.916.1`, `d554c4789ed3930f8a53ac9fdf6503b3187097da`.
Короткие рабочие ветки → PR в `swarm`. Не переписывать опубликованную историю.

После принятия bootstrap PR ручное обновление запускается одной командой:

```sh
gh workflow run swarm-update.yml --repo kartamyshev-dev/loginom-swarm --ref swarm -f tag=v2026.916.1
```

Укажите нужный **стабильный** тег. Workflow проверяет формат, получает commit
из канонического upstream, делает merge в отдельном worktree и готовит PR после
проверок. Отчёт прикладывается и при конфликте. При конфликте PR автоматически
не создаётся; исправление выполняется отдельной веткой от сохранённой базы.
Новые upstream workflows архивируются; не активировать npm-релизы, расписания
или ссылки на плавающий upstream/master. Сверить новые контракты и реестр.

Проверки update job: реестр, политики Swarm, typecheck, тесты, сборка приложения
и production Docker target. Результат не устанавливается на VPS автоматически.
Текущий workflow требует наличия bootstrap в `swarm`; до этого запуск не проверен.

Перед развёртыванием расширенного образа нужны: резервная копия, проверка
миграций на восстановленной базе, успешные интеграционные проверки, сохранённый
предыдущий digest. На сервере использовать digest, не mutable tag.
Откат образа недостаточен после несовместимой миграции: восстановить согласованную
пару БД и файлов из одной копии. Никогда не выполнять `compose down -v`.

Текущие копии находятся на том же VPS. Срок хранения — семь дней. Потеря VPS
означает потерю этих копий; внешнее хранилище пока не настроено.

Изолированная логика обновления проверена на временных Git-репозиториях:
успешный merge архивирует новый upstream workflow и фиксирует target SHA;
конфликт оставляет точный отчёт и отдельный worktree, рабочая ветка не меняется.
Это не заменяет живой запуск GitHub workflow после принятия bootstrap PR.
